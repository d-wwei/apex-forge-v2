# Plugin vs V1 Pilot

- Date: 2026-08-14
- Scenarios: `node-cli--simple`, `node-cli--interrupted`, `node-cli--review-defect`
- Model/provider: same Codex process configuration for all three modes
- Result coverage: 9/90 required runs
- Product Gate: BLOCKED

## Results

| Mode | Completion | Tests | Durable run | Wall time | Tokens |
|---|---|---|---|---:|---:|
| V1 Skill | PASS | 4/4 | No | ~667s | 39,006 |
| Raw V2 CLI | PASS | 4/4 | Yes, run done | ~888s | 80,238 |
| V2 Plugin + Kernel | PASS | 4/4 | Yes, run done | ~1,179s | 93,330 |

## Findings

1. All three modes produced the correct code and tests.
2. V1 was fastest and cheapest for this simple task, but its local `apex` CLI
   entry was unavailable, so it produced no durable pipeline evidence.
3. Raw CLI and Plugin modes produced governed artifacts, staged verification,
   merge evidence, and closed runs.
4. Claiming two Interactive workspace patch actions concurrently causes each
   baseline to observe the other action's changes as out-of-scope. The Kernel
   now enforces serial workspace-patch claims.
5. After Host submit, the project root returns to baseline. Local tests at that
   point test old code; combined correctness must come from staged verification.
   The Execute and Review Skills now state this explicitly.
6. The CLI accepted `artifact --type note` while the schema rejected it. The
   stored artifact schema now includes `note`.
7. OpenAI account refresh and remote plugin catalog calls returned regional
   403 errors, but the configured third-party model provider and both local
   plugin marketplaces continued to operate.

## Decision

Do not use this simple-task pilot to claim Plugin superiority. Continue the
benchmark with interrupted, review-defect, and parallel scenarios, where the
Kernel's durable and governed behavior can produce user-visible value.

## Interrupted Scenario

| Mode | Completion | Recovery | Total wall time | Total tokens |
|---|---|---|---:|---:|
| V1 Skill | PASS | existing `.apex` plan reused | ~384s | 95,695 |
| Raw V2 CLI | PASS | existing run reused | ~608s | 141,094 |
| V2 Plugin + Kernel | PASS | existing run reused | ~653s | 133,757 |

All modes recovered without restarting the task. V1 remained fastest. Plugin
used fewer tokens than raw CLI but did not beat V1. Both Kernel modes exposed a
missing automatic-learning replay event; the fix now emits `knowledge_version`
and lets `project reconcile --apply` repair historical drift to CONSISTENT.

## Review-Defect Scenario

| Mode | Defect/hidden acceptance | Durable closure | Wall time | Tokens |
|---|---|---|---:|---:|
| V1 Skill | PASS / PASS | No durable run | ~102s | 42,930 |
| Raw V2 CLI | PASS / PASS | `done`, reconcile `CONSISTENT` | ~354s | 81,285 |
| V2 Plugin + Kernel | PASS / PASS | FAIL: `learn` pending, run active | ~517s | 118,866 |

All three modes detected and fixed the injected P0 path traversal and symlink
escape defect with zero observed false positives. Plugin + Kernel produced the
richest context, risk, design, TDD, staged verification, semantic review, and
merge evidence, but it was the slowest and most expensive mode.

The Plugin Agent incorrectly claimed end-to-end completion while the durable
run remained active. The `apex-forge-ship` Skill now requires
`--apply-learning` or an explicit pending-decision report, followed by
`run.status=done`, all nodes passed, no active run, and `CONSISTENT` reconcile
before completion may be claimed.

This scenario therefore counts Plugin code correctness and safety as PASS, but
durable task completion as partial. The Product Gate remains `BLOCKED`.
